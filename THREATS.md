# TrustVault threat table

Scope: FastAPI, MySQL/SQLAlchemy, browser JavaScript and private filesystem storage. The backend is the authorization boundary; hidden buttons and unguessable IDs are not security controls.

| # | Threat | How it could happen | Defence | Where | Test |
|---|--------|--------------------|---------|-------|------|
| 1 | IDOR / BOLA through changed document IDs | A logged-in user changes the document ID in a URL or API call to read, download, edit, delete or share someone else's file. | Document routes check ownership or current viewer permissions before returning file bytes or changing permissions. Admin role alone grants no document access. | `backend/main.py` → `has_document_permission`, `update_document_metadata`, `delete_document`, `share_document`, `revoke_document_permission`, `view_document`, `download_document` | `test/test_document_workflow.py::test_owner_document_sharing_workflow`; `test/test_document_workflow.py::test_admin_user_management_and_suspension` |
| 2 | Privilege escalation | A viewer calls owner/admin APIs directly, or sends an elevated role during registration or an update. | Registration schema permits only `owner` or `viewer`; role-protected routes check the active user's role. Admins are provisioned through local CLI functions, not public registration. | `backend/main.py` → `RegisterRequest`, `get_current_user`, `require_role`, `update_admin_user`; `backend/create_admin.py` → `create_initial_admin`; `backend/add_admin.py` → `add_admin_account` | `test/test_document_workflow.py::test_owner_document_sharing_workflow`; `test/test_document_workflow.py::test_admin_user_management_and_suspension`; `test/test_admin_password_reset.py::test_add_additional_admin` |
| 3 | Revoked viewer keeps access | The viewer reuses a document ID, a copied link or an open page after the owner revokes access. | No signed document URLs are issued. Each new view/download checks the current database permission; revocation deletes the permission row. JWTs contain no document permissions. An already-delivered or in-flight response cannot be recalled. | `backend/main.py` → `has_document_permission`, `get_shared_documents`, `revoke_document_permission`, `view_document`, `download_document` | `test/test_document_workflow.py::test_owner_document_sharing_workflow` |
| 4 | Direct file URL or path traversal | An attacker guesses `/uploads/...` or uploads a filename like `../../x`. | Static serving is mounted only on `frontend/`. Upload filenames are reduced to a basename, stored names use UUIDs, and resolved file paths must remain under `UPLOAD_DIR`. | `backend/main.py` → `upload_document`, `get_private_file_path`, `view_document`, `download_document`, `app` | `test/test_document_workflow.py::test_owner_document_sharing_workflow` |
| 5 | Malicious upload and MIME/extension spoofing | An owner uploads an oversized, mismatched or executable file with a fake name or MIME type. | File content is limited to 10 MiB (oversize returns 400); the request body cap is 10 MiB + 64 KiB (excess returns 413). Extensions are allowlisted. PDF/PNG/JPEG checks inspect leading signatures; TXT must be UTF-8 without NUL. Declared MIME must be empty, `application/octet-stream`, or match the detected type, which is stored. These checks are not a full file parser or malware scan. | `backend/main.py` → `UploadRequestSizeLimitMiddleware`, `upload_document`, `detect_file_content_type` | `test/test_document_workflow.py::test_owner_document_sharing_workflow`; `test/test_document_workflow.py::test_upload_request_limit_enforces_stream_without_content_length` |
| 6 | Audit log alteration or truncation | Someone with database access edits or deletes events, or recomputes hashes. | Audit events use a keyed HMAC chain, serialized append locks, ORM update/delete guards, and a signed head anchor. Verification checks record hashes, chain links, and the database head against the anchor. ORM guards do not prevent direct SQL changes; the default anchor is local, not an off-host backup. | `backend/audit.py` → `_acquire_audit_lock`, `create_audit_log`, `_prevent_audit_log_mutation`, `_prevent_bulk_audit_log_mutation`, `_write_anchor`, `_read_anchor`, `verify_audit_chain` | `test/test_document_workflow.py::test_owner_document_sharing_workflow`; `test/test_audit_integrity.py::test_new_audit_events_are_linked_and_verified`; `test/test_audit_integrity.py::test_audit_verification_detects_modified_record_and_invalid_hash`; `test/test_audit_integrity.py::test_audit_verification_detects_broken_previous_hash`; `test/test_audit_integrity.py::test_concurrent_audit_appends_remain_serialized_and_verifiable` |
| 7 | Failed-login abuse and credential guessing | Repeated password guesses, or many account names tried from one IP. | Bad credentials return generic 401; suspended accounts return 403. The database throttle allows up to 5 attempts per account+IP and 20 per IP per 15-minute window before 429 with `Retry-After`. Bucket keys are HMACed. Login failures are audited without passwords. | `backend/main.py` → `login_user`; `backend/login_throttle.py` → `reserve_login_attempt`, `reset_account_ip_attempts` | `test/test_document_workflow.py::test_login_rate_limit_is_persistent_and_expires` (test overrides thresholds to 2/4; does not assert production constants 5/20) |
| 8 | JWT theft and replay | A stolen bearer token is replayed. | Tokens expire (30 minutes by default, configurable). Each authenticated request checks signature/expiry, revocation, account status, and auth version. Logout stores the token fingerprint until expiry. Audit details do not include bearer tokens. | `backend/auth.py` → `create_access_token`, `verify_access_token`, `fingerprint_access_token`, `get_access_token_version`; `backend/main.py` → `get_current_user`, `logout_user` | `test/test_document_workflow.py::test_owner_document_sharing_workflow`; `test/test_admin_password_reset.py::test_reset_admin_password` |
| 9 | CSRF, XSS and CORS | A hostile site triggers actions, or document metadata runs as script. | Authentication uses an `Authorization: Bearer` header rather than cookies. CORS allows only `http://127.0.0.1:5500` and `http://localhost:5500`. Dashboard metadata is placed in text nodes rather than interpreted as HTML. | `backend/main.py` → `app`, `security`, `get_current_user`; `frontend/dashboard.html` → `renderDocuments` | `test/test_document_workflow.py::test_owner_document_sharing_workflow`; `test/test_document_workflow.py::test_dashboard_uses_text_nodes_for_untrusted_metadata` |
| 10 | Database or storage exposure | Stolen credentials, backups or filesystem access. | Database settings are read from environment variables (including `.env`, which `.gitignore` excludes from Git). Uploaded files are outside the frontend static directory and are returned only through authorized view/download routes. This does not protect a stolen `.env`, backup, or compromised host filesystem. | `backend/database.py` → `database_url`; `.gitignore` → `.env` ignore rule; `backend/main.py` → `UPLOAD_DIR`, `get_private_file_path`, `view_document`, `download_document`, `app` | `test/test_document_workflow.py::test_owner_document_sharing_workflow` (private URL only); NO TEST for `.env`/Git-ignore exposure |
| 11 | Administrator misuse | An admin abuses account management or audit visibility. | Admin routes require an active admin. Admins have no implicit document access. User role/status changes create an `ADMIN_USER_UPDATED` audit event. | `backend/main.py` → `get_current_user`, `require_role`, `update_admin_user`, `view_document`, `download_document` | `test/test_document_workflow.py::test_admin_user_management_and_suspension` (admin gating, document access, and audit details for role/status changes) |
| 12 | Error and metadata disclosure | Varying IDs or actions reveals names, paths or permission state. | Denied document requests are audited. Cross-owner denials return no document bytes or storage path; responses use generic not-found/permission errors. | `backend/main.py` → `audit_security_requests`, `_record_security_request`, `view_document`, `download_document`, `update_document_metadata`, `share_document`, `delete_document` | `test/test_document_workflow.py::test_owner_document_sharing_workflow` |
| 13 | Concurrent permission changes | A download races an owner revoking access. | Each newly handled request checks the live permission row before opening the file. Authorization is not locked through file streaming, so revocation after that check may not stop an already-authorized in-flight response. | `backend/main.py` → `has_document_permission`, `revoke_document_permission`, `view_document`, `download_document` | `test/test_document_workflow.py::test_owner_document_sharing_workflow` confirms that requests started after revocation are denied; an already-authorized in-flight response remains an accepted limitation. |
| 14 | Audit/database backup and recovery | A restore omits later audit rows, or the anchor and database come from different points in time. | Verification checks the HMAC chain and compares the database head with the signed anchor, reporting missing or mismatched history. The default anchor is local, so it is not an independent backup. | `backend/audit.py` → `_read_anchor`, `verify_audit_chain`; `backend/main.py` → `verify_audit_logs` | `test/test_document_workflow.py::test_owner_document_sharing_workflow`; `test/test_audit_integrity.py::test_admin_verification_is_protected_and_reports_invalid_chain` |

## Known audit finding

Read-only verification of the configured MySQL database on 2026-11-08 examined
512 records (IDs 3–514). Records 3–446 failed verification; records 447–514
form an 68-record suffix whose hashes and links validate with the current
signing key. The signed anchor is valid and matches database head 514. The
failure begins at record 3, so later valid suffix records do not make the full
history trustworthy.

No historical verification key is configured. Without the original signing
key, the failed prefix cannot be authenticated or safely reconstructed. Do not
re-sign, delete, truncate, or relabel those events as verified. No audit rows or
anchor were changed during this validation. Keep the history marked invalid
unless the original historical key is recovered and verification succeeds.
Operational closure means the finding is accurately documented and preserved;
historical authenticity remains unproven, not repaired.
